# 第 4–6 项的实施与验收

讨论稿 v0.5 · 2026-11-05

工作台以多个 QQ 机器人为入口。操作者从机器人进入一个群或私聊，查看真实收发，打开对应 DSH Session 继续工作，再按需把原生回答发回 QQ。第 4–6 项在 #118 中作为可独立验证的工作台提交。

## 当前实现

- 从 DSH 左侧进入「QQ 机器人」。旧账号继续使用原绑定。在机器人栏可添加另一台机器人、单独启停或更换第二台凭据。第二台的群聊和私聊默认使用空白名单，填入对应 OpenID 后即可接收。
- 在所选机器人的会话树中展开群聊或私聊。点对话会切换工作台内容，点 Session 会打开 DSH 原生对话。当前与历史关联来自已保存的 Session ID，并由宿主持久化确认。通过 QQ `/new` 换新后，旧 Session 保留，下一条成功创建 Session 的消息决定新的当前接收项。
- 「会话设置」占用工作台右侧一列。保存备注只改变展示名称。暂停接收会拦截下一条消息、命令及尚未提交的 QQ 回复；恢复接收仍需通过账号准入规则。冲突时保留草稿。窄屏在工作台内切页。
- 账号启停与第二台凭据更新只影响目标账号。旧主账号的绑定与配置编辑仍使用原 profile 的热重载路径。工作台内新建时选择工作区与预设、完整的新会话默认设置和网页显式回传属于后续提交。

- 第三列展示已准入且启用保存的 QQ 入站，以及实际提交到 QQ 的出站。正文从部署后开始采集，可在右栏关闭新增。原生 DSH 历史与 QQ 投递防重账本分别保留。流式按一次回复更新，QQ 接口接受和实际送达是不同状态。普通群消息能否进入流水取决于 QQ 平台实际推送。

## 固定依赖与验收范围

当前设计分支保存讨论稿。`7969384` 是已验证的投递基线，基于包含 #113 的上游 `0ddf232`。工作台在此基线上追加。旧 ④⑤⑥ 用作交互、迁移和回归样本。 [#113 账号访问](https://github.com/tencent-connect/dsh-qqbot/pull/113) · [#118 入站和投递](https://github.com/tencent-connect/dsh-qqbot/pull/118)

工作台使用官方 QQ SDK 和原版 DSH 宿主。首版范围是多账号、四列布局、当前与历史 Session、两层配置、QQ 收发与响应记录、显式回传。Agent 类型由 DSH 预设决定。共享记忆、主动插话、后台任务编排、用量汇总和自动换新各有独立产品范围。

## 提交顺序

1. 定稿交互、数据边界和验收条件。以本页及关联设计稿作为后续提交的检查表。
2. 让被动回复 ID 缓存随 QQ 网关实例创建和销毁。用相同 OpenID 的两实例夹具验证文字、流式和文件的回复候选不串用。
3. 拆出账号运行管理和账号配置读取。保持首个绑定的原配置和文件归属。两个启用账号同时收发，停用一个账号后复查旧运行代次的待发请求。
4. 在当前绑定写入路径保存历次 Session ID，按账号与对话列出已知关联。新建校验工作区与预设，并在原生 Session 可用后再切换当前绑定。
5. 接入宿主工作台入口、会话树、原生跳转和固定设置栏。账号表单绑定显式 AppID。对话表单按版本保存，区分下一条、下一轮和下次新建生效。
6. 从获准入站与实际投递构建消息时间线和响应查询。复用投递守卫实现从原生回答预览、确认和回执。重放、撤权和未知结果须有回归。

同一个账号只运行一个网关代次。同一个原生 Session 只归一个可接收对话。UI、持久设置和活动网关分别通过明确的 AppID 或 Session 归属通信。校验一个账号停用时另一账号可继续送达，再并行开发只读投影与界面。

## 按能观察的结果推进

| 阶段 | 实现单元 | 验证通过才继续 |
|---|---|---|
| A | 账号目录、旧绑定迁移、独立网关与状态 | 同时连接两个模拟账号，用相同形状的群 ID、用户 ID 和事件 ID 发消息。回执、白名单、配对、回复窗口及媒体互不串用。停用、换凭据、断线和重启只影响目标账号。用实际旧 profile 样本证明 Session ID 与原权限保留。 |
| B | 四列入口与当前、历史 Session | 点击群或联系人加载 QQ 时间线。点击 Session 打开原生页面，返回保留位置。新建成功才变更接收绑定。失败、重复确认、归档与忙碌均有确定反馈。保留旧私聊历史和工作区回退修复。 |
| C | 机器人设置两页、固定会话设置栏 | A 修改新对话默认值后，B 和 A 的已有对话保留各自值。新对话按预期采用模板。逐项核对下一条、下一轮和新 Session 的生效时机。旧对话首次保存正常，真实冲突保留草稿。撤权挡住下一次工具、命令与投递。 |
| D | QQ 时间线、响应记录和显式回传 | 未触发的已接收群消息可查。网页局部操作和仅在 DSH 的内容没有出站气泡。流式、工具、文件和手动发送各有真实回执。翻页、状态更新、连点、超时和重启后保持去重。 |
| E | 隔离验收和评审材料 | 打包安装后在原版 DSH 的独立 profile 实查。用明暗、窄屏截图及操作录屏覆盖四列和设置折叠。真实 QQ 平台按已授权账号核对群聊和私聊，平台限制单独记录。 |

优先证明阶段 A。只有在两个账号的 WebSocket、HTTP、工具路由和持久状态均可独立观察后，才把四列界面接到生产路径。阶段 B 先走通一个开发群的「打开当前 Session」和一段历史，再验证私聊和切换账号。固定设置栏在窄屏切换为工作台内页，返回时恢复原对话和草稿。

开始实现前，把阻塞项固定为双账号隔离和目标宿主接口核验。之后，纯 UI 可以用约定的状态样本制作，服务端以独立夹具推进。账号目录写入、当前 Session 切换和单次外发分别由对应服务串行确认。先让一个开发群走通，再用同一路径接私聊和第二个账号。

## 交付前按场景验收

| 场景 | 通过条件 |
|---|---|
| 账号开关与恢复 | A 的未发投递被拦截，B 继续收发。恢复 A 后的新消息正常，旧消息无回放。换绑时旧运行代次失效。 |
| 日常 Coding | 选工作区与预设，QQ群和私聊都能进入自己的原生 Session。工具和审批留在原生页面。确认后的回答只发到预览中的机器人与 QQ 对话。 |
| 默认值与覆盖 | 对比模板、旧对话和新对话。更改模型强度不触碰其他账号或宿主默认。新 preset 只在新 Session 生效。关流式后下一轮私聊静态回复，群聊提示实际路径。 |
| 准入与撤权 | 账号白名单、对话接收和命令开关分别验证。关闭或撤销后排队的任务、等待中的投递和审批后的工具都复查。 |
| 记录与投递 | 平台接受、失败和结果未知有对应证据。历史只打开原 Session。分页保持锚点。清理正文后仍拒绝重放旧发送操作。 |
| 交互与可访问性 | 头像栏和设置栏可收缩，账号与对话设置各有标题。宽屏折叠扩宽消息列，窄屏返回保留阅读位置，均保持焦点与草稿。键盘可完成切换、保存和取消。 |
| 负载与证据 | 与 #118 在同一夹具比较正常收发和两个账号同时收发。消息页按固定页大小读取，打开单个对话不读取其他账号正文。报告明确区分自动测试、真实 SDK、真实宿主和真实 QQ 平台结果。 |

隔离环境用新 profile、数据目录、工作区和端口。保留 3194 的 #113 与 3195 的 #118 作为已知基线。真实 QQ 验证时避免同一账号在两个环境同时接收。上线候选按自身 SHA 打包和验收，不能以旧 456 的截图或集成版结果代替。
